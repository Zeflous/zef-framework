# Publishing a GitHub Wiki API index

This repository's API reference is generated by **Doctum** and published to
**GitHub Pages** by `.github/workflows/pages.yml`
(`https://zeflous.github.io/zef-framework/api/`).

`.github/workflows/wiki.yml` is an **optional, manually triggered** companion
job that mirrors a *Markdown index* of that reference into the repository's
GitHub Wiki. It is off by default and never runs on a push or a pull request.

## Why only an index, not the documentation

A GitHub Wiki is a **separate git repository** (`<repo>.wiki.git`) that stores
**Markdown** pages. A Doctum build is static **HTML** plus asset trees. The
following cannot be carried over:

| Doctum artefact | Wiki |
|---|---|
| per-type `.html` pages | Wiki renders Markdown, not HTML |
| `css/`, `js/`, `fonts/`, `doctum.js` | the Wiki supplies its own CSS; no custom JS |
| `opensearch.xml`, `search.html` | no custom search |
| relative `href="Zef/..."` links | the Wiki resolves *page names*, not paths — relative links break |
| `doctum-search.json` | **plain JSON — the one artefact that survives** |

So `scripts/ci/doctum_to_wiki.py` reads `doctum-search.json` and writes one
Markdown page per namespace, with every entry linking out to the real API page
on GitHub Pages. The Wiki becomes a navigable index over the documentation
rather than a degraded copy of it.

## Enabling it

The job is deliberately double-gated, so it can never publish by accident.

1. **Create the Wiki.** A repository's `.wiki.git` does not exist until its
   first page is created. Open the **Wiki** tab and save any page (the default
   "Welcome" page is fine). Until then every clone of `.wiki.git` fails with
   `remote: Repository not found.` — which the workflow treats as a *controlled
   skip*, not an error.
2. **Enable Wiki write access.** The workflow pushes to a *different*
   repository from the one it runs in, which `GITHUB_TOKEN` is not scoped for.
   Add a repository secret named `WIKI_TOKEN` holding a token that can write to
   the wiki (a classic PAT with `repo` scope, or a fine-grained token with
   **Contents: read and write** on this repository, which also covers its wiki).
   *The secret holds a credential: set it in repository settings, never in a
   file, and never echo it in a workflow step.*
3. **Run it by hand.** Actions → **Wiki API index** → *Run workflow* → set
   **publish** to `true`. With `publish` left at its default `false` the job
   generates and prints the index (uploaded as a build artefact) but pushes
   nothing.

## What each outcome means

| Situation | Workflow result |
|---|---|
| Wiki not created yet | **controlled skip** — notice, exit 0, no push |
| `WIKI_TOKEN` not configured | **controlled skip** — notice, exit 0, no push |
| `publish` left `false` | index generated + uploaded as artefact, no push |
| index is empty | **failure** — refuses to publish an empty index |
| all gates pass, `publish: true` | Markdown index pushed to the Wiki |

## Keeping it honest

* `_Sidebar.md` is regenerated on every run, so Wiki navigation always matches
  the current namespace list.
* The index is derived from the same build that Pages serves, so the two cannot
  describe different APIs — provided the job is run after a Pages deploy.
* Nothing in this job writes to the default branch, and it never touches the
  required status check `Build API documentation` (`docs-check.yml`), because it
  does not run on `pull_request` at all.
